# Dupli-Annihilator-G v1.3.8

## Executive Summary

`v1.3.8` delivers a comprehensive UI performance overhaul. The entire frontend is refactored to eliminate wasted renders during active job execution — form panels, the header, and the update banner now produce **zero re-renders** per polling tick while a job is running.

---

## Performance: UI Render Elimination

### Root Cause

The entire UI previously lived in a single monolithic `App()` component with 16+ `useState` variables. The 300ms event-polling loop called `setProgress()` on every batch, causing the full component tree to re-render — including form panels that had no dependency on progress data whatsoever. During a typical job this produced ~3–4 full re-renders per second across all UI sections.

### Changes Applied

| Change | Impact |
|---|---|
| Job state consolidated into `useReducer` | Multi-field transitions (e.g. `startJob`) go from 4 sequential `setState` calls to 1 atomic `dispatch` |
| 6 sections extracted as `React.memo` components | `Header`, `UpdateBanner`, `InputSection`, `ProcessingSection`, `OutputSection`, `SummaryScreen` |
| `localeRef` pattern in `pollEvents` and `checkForUpdates` | Polling interval no longer restarts when user changes language |
| All event handlers wrapped in `useCallback` | Stable references allow `React.memo` to correctly bail out |
| `NEXT_EVENTS_REQ` module-level constant | Eliminates one object allocation per 300ms poll cycle |

### Measured Effect

During an active job (job running, polling at 300ms):

| Component | Re-renders/sec before | Re-renders/sec after |
|---|---|---|
| `InputSection` | ~3–4 | **0** |
| `ProcessingSection` | ~3–4 | **0** |
| `OutputSection` | ~3–4 | **0** |
| `Header` | ~3–4 | **0** |
| `UpdateBanner` | ~3–4 | **0** |
| `TelemetryFooter` | ~3–4 | ~3–4 (expected — shows live progress) |
