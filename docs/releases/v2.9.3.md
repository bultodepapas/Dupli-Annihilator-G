# Dupli-Annihilator-G v2.9.3

## Executive Summary

`v2.9.3` improves the startup experience for rich inputs, especially large EPUB batches. The desktop app now shows visible extraction progress from the first stage of the job, and the EPUB extraction path has been optimized to reduce unnecessary allocations and copying.

---

## Feature: Visible Extraction Telemetry

Jobs that begin with `EPUB` or `PDF` extraction no longer look idle while preprocessing is running.

### What changed

- the telemetry footer now shows extraction progress before tokenization starts,
- extraction reports the current rich-file index and total rich files,
- the current input path is shown while a file is being extracted,
- the frontend polls once immediately after `start_job` so the first visible state arrives sooner.

### Why it matters

Previously, large rich-input jobs could spend a long time in preprocessing while the UI still showed `0/0` files and `0` tokens. Users now get immediate confirmation that work is underway and which file is being processed.

---

## Improvement: Faster EPUB Extraction

The EPUB text extraction path was rewritten to reduce overhead before the deduplication engine starts.

### What changed

- chapter text is now streamed into a buffered writer,
- HTML/XML tag stripping is done in a single pass,
- common entities such as `&amp;`, `&nbsp;`, `&lt;`, `&gt;`, `&quot;`, and `&apos;` are decoded inline,
- cancellation checks now happen between EPUB chapters/resources.

### Why it matters

This reduces CPU and allocation overhead when many EPUBs are loaded at once and improves cancellation responsiveness during extraction.

---

## Improvement: Better AUTO Mode Choice For Rich Inputs

`AUTO` mode now decides between `RAM` and `DISK` after rich inputs have been resolved to their extracted text form.

### Why it matters

Compressed EPUB containers can be much smaller than the text they expand into. Basing the mode decision on the resolved text gives a more accurate memory estimate and avoids overly optimistic `RAM` choices for large rich-input jobs.
